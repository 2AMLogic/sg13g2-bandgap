# Two-row top-level placement (issue #177)

Before/after for re-placing both top-level assemblies' three leaf cells from
a single left-to-right row into **two rows around a shared routing channel**,
and for the routing-invariant rewrite that placement required.

This is step 2 of the two-step plan issue #173 opened, and the direct
follow-on to [`../2026-09-resistor-fold/`](../2026-09-resistor-fold/README.md).
That entry's §3 measured 51.6% / 56.6% of each post-fold assembly as
whitespace and named the two mechanisms responsible — *the inter-cell routing
channel* and *single-row placement* — and its §6 ("Not done, and why")
recorded that the second was deliberately left alone because both assemblies'
routing rested on the three cells occupying disjoint x-ranges. This entry is
the same measurement re-taken after both mechanisms were addressed.

**This is not a spec change and not a conformance claim.**
`spec/porting-plan.md` §6's `Area | < 0.05 mm²` row is drafted and unratified
(#125, PR #128), and `measure_area.py` deliberately emits no verdict. The
numbers below are geometry measurements, exactly as the two prior records
were.

Method, provenance and per-cell field definitions are unchanged — see
[`../2026-09-layout-area/README.md`](../2026-09-layout-area/README.md). Both
sides of every table below come from the same script
(`measurements/2026-09-layout-area/measure_area.py`), the same `klt stats`
call, and the same committed-GDS inputs; only the GDS differs.

- **Before** = `layout/**.gds` at `fe97115` (`main` at the point this branch
  was cut — i.e. **after** #173/PR #178's fold and re-pack and after
  #179's LVS-narrative re-audit).
- **After** = the same files as regenerated by this issue.
- `klt` for both sides: `klt 0.3.0+gc6dbf66c53c6` — the *same* binary, run
  twice, so no part of the delta below is tool drift.
- Only the two assemblies' `generate.py` were touched. **No leaf cell's own
  GDS changed** — `git status` after regenerating everything lists neither
  `bandgap_{core,amp,startup}.gds` nor their three `sg13cmos5l-*`
  counterparts, and rows 1–3 and 5–7 of §2 below are byte-identical on both
  sides.

## 3. Where the whitespace went

The same headline metric the two prior records use — assembled footprint
against the sum of its own leaves' footprints:

| assembly | Σ leaf footprints (µm²) | assembled (µm²) | ratio | whitespace |
|---|---|---|---|---|
| `bandgap_top`, before | 20,354.1 | 46,920.4 | 2.30× | 56.6% |
| `bandgap_top`, after | 20,354.1 | 28,305.5 | **1.39×** | **28.1%** |
| `sg13cmos5l_bandgap_top`, before | 23,067.2 | 47,635.6 | 2.07× | 51.6% |
| `sg13cmos5l_bandgap_top`, after | 23,067.2 | 33,607.5 | **1.46×** | **31.4%** |

Both mechanisms the prior entry named moved, and both moved for the reason it
predicted:

1. **The inter-cell routing channel is shorter *and* thinner.** It used to
   span the assembly's whole width above the row (482 / 503 µm) at a 5 / 6 µm
   bus pitch; it now spans at most 224 / 248 µm at a 3 / 2.5 µm pitch. On
   SG13G2 that is 5 buses in 12 µm of bar-to-bar span where #173 needed 20;
   on CMOS5L, 5 buses (`sns2` gained one, see §6) in 10 µm where #173's 4
   needed 18.
2. **Single-row placement is gone.** The tallest leaf no longer sets a height
   the two shorter ones have to pay for across the full width.

Because the remaining whitespace decomposes exactly into the two rows' bands
plus the channel between them, it is worth stating as an identity rather than
an estimate. For each assembly, `width × (row A band + channel band + row B
band [+ port strip]) = footprint`:

**`bandgap_top`** — 223.60 µm wide:

|---|---|---|---|---|---|
| row A (`amp`) | −1.59 … 32.175 | 33.77 | 7,549.9 | 7,289.9 | 260.0 |
| routing channel | 32.175 … 49.9 | 17.73 | 3,963.3 | 0 | 3,963.3 |
| row B (`core`, `startup`) | 49.9 … 123.62 | 73.72 | 16,484.5 | 13,064.2 | 3,420.3 |
| `vref` port strip | 123.62 … 125.0 | 1.38 | 307.9 | 0 | 307.9 |
| **total** | | **126.59** | **28,305.5** | **20,354.1** | **7,951.4** |

**`sg13cmos5l_bandgap_top`** — 248.00 µm wide:

| band | y-range | height (µm) | area (µm²) | leaves inside (µm²) | free (µm²) |
|---|---|---|---|---|---|
| row A (`core`) | −3.21 … 61.7 | 64.91 | 16,097.7 | 14,933.8 | 1,163.9 |
| routing channel | 61.7 … 78.76 | 17.06 | 4,230.9 | 0 | 4,230.9 |
| row B (`amp`, `startup`) | 78.76 … 132.30 | 53.54 | 13,278.9 | 8,133.4 | 5,145.5 |
| **total** | | **135.51** | **33,607.5** | **23,067.2** | **10,540.3** |

So of what is left: the channel is 14.0% (SG13G2) / 12.6% (CMOS5L) of the
assembled footprint, the side corridors that carry risers past the rows are
0.9% / 3.5%, and the rest is *within-row* slack — the gap between two
same-row neighbours plus the shorter leaf's unused height. On CMOS5L that
within-row slack (5,145.5 µm², 15.3%) is now the single largest remaining
item, and it has an obvious shape: row B is 191.4 µm of leaf across a 248 µm
assembly, because row A's `core` is 230 µm wide on its own. Naming it is not
the same as proposing to fix it — see §6.

## 4. The routing invariant this required, and how it was checked

Issue #173 stopped short of this placement for a specific, stated reason:
both assemblies' inter-cell routing was documented as resting on the three
cells occupying **disjoint x-ranges**, so a vertical route drawn within one
cell's x-span could only collide with that same cell's geometry. Two rows
break that premise outright. The replacement, written into both modules'
docstrings rather than the old paragraph merely being deleted, is a
two-dimensional form of the same argument plus one genuinely new obligation:

1. **Row disjointness** — the two rows occupy disjoint y-bands separated by a
   channel that holds no leaf geometry at any x; cells *within* a row are
   still x-disjoint.
2. **Risers never leave their own row** — every riser runs from its own
   cell's pad to its own net's bus in the channel and stops, so its y-extent
   lies in its own row's band plus the channel. By (1) the only leaf geometry
   it can meet is its own cell's. That is exactly what the old invariant
   bought, re-derived on (row, x) instead of x alone.
3. **Globally distinct riser columns** — the new obligation. Risers from
   *both* rows now share the channel, so two different nets may not share a
   column anywhere in the assembly, not merely within one cell. Under the old
   invariant this was automatic; it now has to be enforced.

(3) is **machine-checked, not asserted**: both generators call an
`_assert_column_pitch()` that raises if two different nets' riser columns
come within 2.0 µm, and every column each `_route*` function chooses is
registered with it. A `klt drc`-clean layout is not evidence against this
class of bug — two overlapping same-layer shapes merge into one clean
polygon that violates no width or space rule — which is the same failure mode
`bandgap_top/generate.py`'s own `LANDING_UM` comment documents for
leaf-internal crossings.

The columns as placed (all figures in each assembly's own global µm):

| net | `bandgap_top` core / amp / startup | `sg13cmos5l_bandgap_top` core / amp / startup |
|---|---|---|
| `vdd` | −10.5 / 95 / 159.7 | 90 / 80 / 95 |
| `vss` | 30 / −3 / 170 | 222 / 30 / 165 |
| `fb` | −5.6 / 140 / 180 | −15 / −9 / 187 |
| `sns1` | −15.5 / 50.6 / 154.4 | −18 / 85 / 148 |
| `sns2` | −8 / −18 / — | 229 / −12 / — |
| `vref` | 120 / — / — | 225 / — / — |

Closest different-net pair: 2.4 µm (`bandgap_top`, core `fb` at −5.6 vs core
`sns2` at −8) and 3.0 µm (`sg13cmos5l_bandgap_top`, `amp.out` at −9 vs
`amp.in_p` at −12).

### The one thing the invariant did *not* catch, and what did

Rule 2 constrains risers — vertical runs. It says nothing about a
*horizontal* run in a corridor, and that is exactly where the first two-row
draft of `bandgap_top` broke: `bandgap_core`'s `vss` leg used to jog sideways
on Metal2 at its own local `y=0` before rising, which was harmless while
every other riser rose *away* from it, but under the two-row floorplan sits
across the corridor at precisely the height every other row-B riser passes
through on its way *down*. `klt drc` reported `clean, 0 violations` on that
draft. `klt extract` reported

```
* pin FB,IN_P,OUT,SNS2,VDD,VSS
```

— four nets merged into one. The fix was structural rather than a
re-columning: `bandgap_core`'s `vss` bar is the lowest Metal2 that leaf owns,
so its leg now drops straight out of the bar's underside with no jog at all.

This is recorded because it is the concrete answer to "why was step 2
separable work": the net-set comparison below is not a formality, it is the
only check that would have caught this.

## 6. What changed in the routing, beyond placement

Recorded because these are behaviour changes a reviewer would otherwise have
to reverse-engineer from the diff:

- **`bandgap_core`'s `vss` leg no longer jogs** (SG13G2) — see §4.
- **`bandgap_core`'s `sns2` leg crosses the cell at local `y=35`** (SG13G2).
  Its pad (local x ∈ [40.5, 57.5]) lies entirely inside that leaf's own
  Metal2 `vss` slab (local x ∈ [−3.05, 125.05], y ∈ [−0.75, 0.75]), so no
  column within the pad can drop to the channel. It rises 13.7 µm to a band
  0.9 µm above the top edge of every Metal2 shape that leaf owns (33.925),
  crosses there, and drops in the left corridor — still entirely inside row
  B's band, so rule 2 holds for it.
- **`sns2` gained a bus on CMOS5L.** #81/#173 routed it as a direct
  three-segment Metal1 dog-leg through the core-amp gap, which worked only
  because `amp` sat immediately right of `core` at the same height. With
  `amp` in the other row, a direct route would have to cross the whole
  channel on the deck's one modelled metal (`metals=((8, 0),)`, `vias=()`,
  klayout-tools#1417). A fifth bus plus two `GatPoly` risers is the answer
  the other four nets already use.
- **All three CMOS5L external ports moved onto geometry the assembly already
  draws.** `vdd`/`vss` are labelled on their own bus at a column that bus
  already spans, rather than extending it out to `x = −40`/`−45`; `vref`'s
  port is a `poly_tab` pad at the top of its own riser rather than a route
  down to `y = −10` and ~275 µm left to `x = −50`. That alone was ~40 µm of
  assembly width and ~7 µm of height spent on three labels.

## 7. Not done, and why

- **Closing the CMOS5L within-row slack (§3, 15.3%).** Row B (`amp` +
  `startup`, 191.4 µm) is narrower than row A (`core`, 230 µm), and `amp` is
  10.6 µm shorter than `startup`. Squeezing it means either splitting `core`
  across both rows or a third row, both of which change the invariant again
  rather than applying it. Not attempted, and not filed as an issue either:
  the remaining ~10.5 kµm² is smaller than the measurement's own honest
  uncertainty about whether a `< 0.05 mm²` draft row wants it.
- **Re-running the three PEX simulation suites.** Both assemblies'
  `.pex.spice`/`.extracted.spice` moved again here (routing lengths changed,
  device parameters did not — §5), so `sim/*-pex/`'s hand-merged extracted
  block is stale for the same reason and to the same degree #173 left it.
  Still tracked as **#176**, which this issue's own sequencing note said
  should land *after* this one precisely so #176 does not have to be redone.
- **Mirroring or rotating any leaf.** Both floorplans are translation-only,
  as they have been since #81. Row assignment was chosen from each leaf's own
  pad band instead (see either `generate.py`'s Floorplan section), which
  reaches the same result without a transform the leaf-level LVS evidence has
  never been run against.

## Reproduce

```bash
python3 layout/bandgap_top/generate.py
python3 layout/sg13cmos5l-bandgap_top/generate.py
git diff --stat                                      # empty: both are deterministic

python3 measurements/2026-09-layout-area/measure_area.py            # print

cd ../sg13cmos5l-bandgap_top
klt drc sg13cmos5l-bandgap_top.gds --deck sg13cmos5l --format json   # clean, 0

  && grep '^\* pin' /tmp/b.spice
```

and fails on drift. The "after" column of every table here is the record that
script wrote (`measurements/2026-09-layout-area/area_record.json`, refreshed
by this issue); the "before" column is the same record as committed at
`fe97115`.
