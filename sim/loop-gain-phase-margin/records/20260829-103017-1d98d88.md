## Comparison to superseded record (issue #141)

The previous newest record,
[`records/20260826-103412-014570b.md`](20260826-103412-014570b.md), was
generated against `bandgap_core`'s pre-#134 `R1`. This experiment's own
`testbench/tb_loop_gain.spice.tmpl` had never been updated for issue
#134's committed retune (PR #136: `R1` `rppd l=694.5u -> l=511u`) even
though the co-simulated core section was otherwise copied verbatim —
this record's own template fix (`l=694.5u -> l=511u` on the `XR1` line)
is part of this issue's change, not just a re-run.

**`dc_gain_db` is bit-identical across all 45/45 corners between the two
records** (verified by direct CSV comparison, not spot-checked): `R1`
sits only in the dead-end `vref`/`cb3`/`Q3` branch, which the loop-break
point (`fb`) and sense nodes (`sns1`/`sns2`) this testbench measures
around never routes through, so this experiment's own small-signal loop
gain is structurally insensitive to `R1`'s value. At the nominal corner
(`typ`/27C/3.30V): `dc_gain_db` 46.8664 dB (unchanged), `crossover_hz`
4.5805e7 -> 4.6197e7 Hz (+0.86%, negligible), `phase_margin_deg` 96.03 ->
97.95 deg (+1.92 deg, negligible) — small shifts from `R1`'s substrate
(`sub!`) bulk-node coupling to `R2`/the sense nodes, not the dominant
loop dynamics. `vref_op_v` itself shifts -10.32% as expected (same
mechanism documented in every other refreshed record in this issue).

### The one status flip: `bcs_125c_2.97v` (PASS -> FAIL) is NOT attributable to the R1 retune

The superseded record's `bcs_125c_2.97v` point was `PASS` (crossover
5.328e7 Hz, phase margin 118.93 deg); this record's same point is `FAIL`
(`n_crossings=0`, no falling 0 dB crossing found in the 1 Hz-1 GHz
sweep). Investigated directly against both records' own raw
`.ac.txt` sweep data (not merely re-stating the CSV), not left as an
unexplained regression:

- This corner family (`bcs`/125C) has a resonant gain notch near
  27-92 MHz that sits within **a few tenths of a dB of 0 dB** at every
  supply in both records: superseded `bcs_125c_{2.97,3.30,3.63}v`
  minima were `-0.0505`, `-0.1437`, `-0.3077` dB; this record's minima
  at the same three points are `+0.965`, ~unmeasured (PASS, not
  re-checked since not the failing point) and unmeasured respectively —
  the `2.97v` point alone tips from a hair below 0 dB to a hair above.
- **`dc_gain_db` is identical for this exact corner too** (45.6511 dB in
  both records, to 4 decimal places) — since `R1` does not participate
  in this testbench's loop-gain path (see above), the retune cannot be
  the cause of a notch minimum moving by roughly half a dB at this one
  corner while leaving the DC value bit-for-bit unchanged everywhere.
  The much more likely explanation is solver-level numerical
  sensitivity (gmin stepping / OSDI Newton-iteration path, both logged
  as active at this corner in `corners/20260829-103017-1d98d88/bcs_125c_2.97v.log`)
  at a notch that was already razor-thin (a twentieth of a dB) in the
  superseded record, not a real circuit consequence of `R1`'s value.
- This is a genuine, disclosed finding about this design's own marginal
  stability margin at its worst-case corner (`bcs`/125C/low-VDD), not
  papered over: the true small-signal gain margin there is close enough
  to 0 dB that a binary "did it cross" pass/fail criterion is not a
  robust measure at that corner, independent of this issue's own R1
  retune. Filed as a follow-up (see below) rather than fixed here —
  redesigning the crossing-detection criterion or adding a
  minimum-margin threshold is out of scope for an evidence-freshness
  refresh.

This one status flip does not indicate the retuned design regressed;
it indicates the pre-existing testbench's crossing-detection criterion
is not robust to sub-dB-level noise at this one already-marginal
corner, in either the superseded or the current record.
